/sbom — Software Bill of Materials generator

Generate standards-compliant SBOMs for a project across many stacks — npm, Python, Go, Rust, Java, containers — without adding a single dependency to the target. Optional quality scoring, vulnerability scan, VEX, and signing.

🧾 Two formats

Emits CycloneDX 1.6 and SPDX 2.3 from one pass — both NTIA- and CISA-endorsed.

🪶 Zero install

npm reads the lockfile directly; other stacks use ephemeral runners. Nothing is added to the project manifest.

♻️ Reproducible

Pin SBOM_TIMESTAMP → byte-identical output, so re-runs are diff-clean.

Overview

An SBOM is a complete inventory of every component a project depends on — direct and transitive — with versions, identifiers, hashes and licenses. It lets you answer “am I shipping the compromised version of X?” in seconds, which is the concrete defense against the 2024–2026 npm supply-chain wave (xz-utils, Shai-Hulud, chalk/debug, Axios RAT).

The /sbom skill is an orchestrator: it detects the project’s stack, routes to the right zero-dependency generator, writes both formats into sbom/, and can optionally score, scan, and sign the result.

detect stack→ generate (CDX + SPDX)→ score→ scan + VEX→ sign→ report

Quick start

# SBOM for the current directory (auto-detect stack)
/sbom

# SBOM for a specific project
/sbom ./path/to/repo

# also score the result against quality profiles (gate ≥ 7.0)
/sbom --score

# also vulnerability-scan the SBOM   (networked, asks first)
/sbom --scan

# also create a cosign attestation   (networked, asks first)
/sbom --sign

Under the hood, the npm path runs the vendored zero-dependency generator:

SBOM_TIMESTAMP="$(date -u +%Y-%m-%dT00:00:00Z)" \
  node .claude/skills/sbom/scripts/generate-sbom.mjs \
  --root ./path/to/repo --out-dir ./path/to/repo/sbom
# → sbom/bom.cdx.json (CycloneDX 1.6) + sbom/bom.spdx.json (SPDX 2.3)

Hard rules

These are enforced on every run — they are what make the skill safe to point at any repo.

1 · Ask before touching a repoOne repo at a time; the plan is shown before anything executes.
2 · Never npm installNo command that modifies the target’s manifest/lockfile. npm reads the lockfile; other stacks use ephemeral runners (npx -y, pipx run, go run …@latest, Docker).
3 · Never guess the stackDetected from files actually read, not assumed.
4 · Outputs land in sbom/And are kept out of the project bundle. Nothing is committed unless you ask.
5 · --scan / --sign are networked & opt-inThey reach external services; the skill states that and gets an explicit OK first.
Never imply completenessIf an SBOM is direct-deps-only, or a stack couldn’t be fully covered, the skill says so explicitly (CISA “Known Unknowns”) rather than presenting a partial result as complete.

Outputs & formats

FileFormatWhy
sbom/bom.cdx.jsonCycloneDX 1.6Security-oriented; native VEX path. Mandatory fields bomFormat + specVersion.
sbom/bom.spdx.jsonSPDX 2.3ISO/IEC 5962 lineage; widest licensing-tool recognition.
Why 1.6 / 2.3 and not the newest CycloneDX 1.7 and SPDX 3.0.1 are released, but as of 2026-06 the major consumers (Dependency-Track, Trivy, Grype) still reject 1.7 and don’t reliably ingest SPDX 3.x. 1.6 / 2.3 are the broadest-consumed targets — a deliberate compatibility choice, revisited as consumers catch up.

Both outputs carry the NTIA seven minimum elements: Supplier, Component Name, Version, Other Unique Identifiers (purl), Dependency Relationship, Author of SBOM Data, Timestamp.

Sample — CycloneDX component (real output) 
{
  "type": "library",
  "bom-ref": "pkg:npm/%40alloc%2Fquick-lru@5.2.0",
  "name": "@alloc/quick-lru",
  "version": "5.2.0",
  "purl": "pkg:npm/%40alloc%2Fquick-lru@5.2.0",
  "scope": "excluded",
  "hashes": [{ "alg": "SHA-512", "content": "52b700…3b0a2f" }],
  "licenses": [{ "license": { "id": "MIT" } }]
}

Dual-license strings are emitted correctly as an expression, e.g. { "expression": "Apache-2.0 AND LGPL-3.0-or-later AND MIT" }. Dev dependencies get scope: "excluded".

How it works — the 6 steps

  1. Detect the stack — glob the target root for manifests/lockfiles (never guess).
  2. Generate — route to the matching generator (npm → vendored reader; others → ephemeral runner / Syft).
  3. Score --score — run sbomqs, flag below 7.0.
  4. Scan --scan — Grype / OSV over the SBOM; offer a VEX for non-exploitable findings.
  5. Sign --sign — cosign attestation.
  6. Report — stacks detected, generator used, component counts, score, findings, and any gap.

Quality scoring --score

Runs the sbomqs scorer as an ephemeral Docker container — nothing installed:

docker run --rm -v "$(pwd)":/sboms \
  ghcr.io/interlynk-io/sbomqs:latest score /sboms/bom.cdx.json
GateTreat ≥ 7.0 on the NTIA Minimum Elements (2021) profile as the pass bar for a lockfile-derived SBOM. A low Licensing/Completeness score is expected for source SBOMs (see Limits) — not a defect.

Optionally cross-check with the SPDX conformance checker:

pipx run ntia-conformance-checker --file sbom/bom.spdx.json

Vulnerability scan & VEX --scan

Feed the SBOM to a scanner (consumes CycloneDX/SPDX directly):

grype sbom:sbom/bom.cdx.json
# or
osv-scanner --sbom=sbom/bom.cdx.json

For findings that don’t actually apply, the skill can draft an OpenVEX document (simpler than CSAF; natively consumed by Grype/Trivy/OSV). VEX statements link to a component by purl:

{
  "@context": "https://openvex.dev/ns/v0.2.0",
  "@id": "https://example.com/vex-0001",
  "author": "your-org",
  "timestamp": "2026-06-18T00:00:00Z",
  "version": 1,
  "statements": [{
    "vulnerability": { "name": "CVE-2023-12345" },
    "products": [{ "@id": "pkg:npm/lodash@4.17.21" }],
    "status": "not_affected",
    "justification": "vulnerable_code_not_in_execute_path"
  }]
}

Sign & attest --sign

Sign the SBOM with Sigstore cosign v3. Keyless/OIDC is the default in CI (COSIGN_EXPERIMENTAL is no longer required):

# standalone SBOM file (blob):
cosign attest-blob --predicate sbom/bom.cdx.json --type cyclonedx sbom/bom.cdx.json

# container image:
cosign attest --predicate sbom/bom.cdx.json --type cyclonedx <image>@<digest>

# verify:
cosign verify-attestation --type cyclonedx \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com <ref>

Provenance (who built it, when, from which source) complements the SBOM (what’s in it). SLSA provenance + in-toto attestations are the higher-assurance tier.

Worked examples

1 · A single npm project

/sbom ./my-app
# Detected: npm (package-lock.json v3, single package)
# Wrote sbom/bom.cdx.json (CycloneDX 1.6) + sbom/bom.spdx.json (SPDX 2.3)
#   — 1066 components (851 runtime, 215 dev).

2 · npm + quality gate in CI

SBOM_TIMESTAMP="$(date -u +%Y-%m-%dT00:00:00Z)" \
  node .claude/skills/sbom/scripts/generate-sbom.mjs --root . --out-dir sbom
docker run --rm -v "$(pwd)/sbom":/sboms \
  ghcr.io/interlynk-io/sbomqs:latest score --json /sboms/bom.cdx.json \
  | jq '.files[0].avg_score' | awk '{ if ($1 < 7.0) { print "below gate"; exit 1 } }'

3 · A monorepo (workspaces) — honest fallback

/sbom ./mono-repo
# WARNING: package.json declares `workspaces` — the zero-dep reader inventories the
# root project only and may under-report members. Routing to Syft for full coverage:
syft dir:./mono-repo -o cyclonedx-json=sbom/bom.cdx.json -o spdx-json=sbom/bom.spdx.json

4 · A Python service (no deps added)

pipx run cyclonedx-py requirements \
  --input-file requirements.txt \
  --output-file sbom/bom.cdx.json --spec-version 1.6

5 · A container image

syft myregistry/app@sha256:<digest> \
  -o cyclonedx-json=sbom/bom.cdx.json -o spdx-json=sbom/bom.spdx.json

Limits & gaps

Source vs build SBOM

The npm path describes declared dependencies from the lockfile — not what a build actually links. Label as source-level when handing off.

Monorepos

The zero-dep reader is single-package. workspaces projects get a warning and should use Syft/cdxgen.

Per-package metadata

Supplier, download location and full license text aren’t in npm lockfiles → lower Licensing/Completeness scores.

Rust spec version

cargo-cyclonedx caps at spec 1.5 — verify the emitted specVersion and normalize if a consumer needs 1.6.

Ephemeral tools must be reachable

Non-npm stacks and --score/--scan/--sign need their tool fetchable/installed; if not, the skill reports the gap rather than faking output.

Private containers

Image pulls may need registry credentials; the skill confirms you’re logged in rather than running docker login for you.

FAQ

Does it add anything to my project?

No. That’s the core promise. npm reads the existing lockfile; every other stack uses an ephemeral runner (npx -y, pipx run, go run …@latest, Docker). Your package.json / requirements.txt / Cargo.toml are never modified.

Why both CycloneDX and SPDX?

Both are NTIA- and CISA-endorsed and different consumers prefer different formats. Emitting both maximizes interoperability at no extra cost (one pass).

Why not the newest spec versions?

CycloneDX 1.7 / SPDX 3.0.1 exist but major consumers (Dependency-Track, Trivy, Grype) still reject 1.7 and don’t reliably ingest SPDX 3.x as of 2026-06. 1.6 / 2.3 are the safe, broadly-consumed defaults.

Is an SBOM legally required?

US OMB M-26-05 (Jan 2026) rescinded the prior federal mandate — SBOMs are now an optional, on-request contractual term. The EU CRA drives obligations from Sep 2026 (reporting) / Dec 2027 (main). Either way, an SBOM is the practical basis for vulnerability response.

How do I make re-runs diff-clean?

Set SBOM_TIMESTAMP to a fixed value. Output is then byte-identical across runs (verified), so committing it produces clean diffs.

Where do the files go?

Into <target>/sbom/ by default (--out-dir to override). They’re meant to stay out of the project bundle; the marketplace .gitignore already ignores sbom/.
